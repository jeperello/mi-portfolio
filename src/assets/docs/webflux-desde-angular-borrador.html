Mi primera experiencia consumiendo una API reactiva con WebFlux desde Angular

Cuando entramos a una página web normalmente esperamos una respuesta completa: hacemos clic en un botón, esperamos unos segundos y recibimos todos los datos juntos. Una API reactiva cambia un poco esta idea: puede comenzar a enviar información apenas la tiene disponible, sin esperar a construir una respuesta enorme.

En este artículo cuento, de forma sencilla, qué aprendí al conectar una aplicación Angular con una API construida con Spring WebFlux.

¿Qué intentaba mostrar?

La demo tiene tres tipos de información:

  • Tecnologías utilizadas para construir la API.
  • Ventajas de utilizar un enfoque reactivo.
  • Métricas de memoria del servidor en tiempo real.

La idea no era solamente mostrar una lista. Quería que el usuario pudiera ver cómo los datos llegan progresivamente desde el backend.

¿Qué significa que una API sea reactiva?

En lugar de pensar únicamente en una respuesta única, podemos pensar en un flujo de datos. Ese flujo puede emitir un mensaje, esperar un momento y emitir otro. El frontend escucha ese flujo y actualiza la pantalla cada vez que llega un nuevo elemento.

Una forma simple de imaginarlo es esta:

El backend no dice solamente: “aquí tienes todos los datos”.

Dice: “aquí tienes el primer dato”, luego “aquí tienes el siguiente” y después “aquí tienes otro”.

La conexión entre WebFlux y Angular

Para esta demostración utilicé Server-Sent Events, conocidos como SSE. El navegador abre una conexión con el servidor y queda escuchando los mensajes que llegan por ella.

Desde Angular, el consumo se realiza mediante EventSource. Cada vez que el servidor envía un evento, Angular recibe el texto, lo convierte desde JSON y actualiza la vista.

Flujo básico:

  1. Angular abre la conexión.
  2. WebFlux comienza a emitir datos.
  3. El navegador recibe cada evento.
  4. Angular actualiza la interfaz.

Una conexión puede permanecer abierta

Durante las pruebas apareció una diferencia importante entre un stream finito y uno continuo.

El stream de métricas está pensado para permanecer abierto, porque el servidor sigue enviando valores nuevos. En cambio, tecnologías y ventajas podrían enviar una cantidad limitada de mensajes, aunque la conexión no se cierre automáticamente.

Esto tiene una consecuencia:

Que dejen de llegar mensajes no significa necesariamente que la conexión haya terminado.

Si el backend mantiene abierta la conexión, el frontend no puede adivinar si el stream terminó o si simplemente está esperando el próximo mensaje. Por eso no conviene utilizar un tiempo de espera como prueba definitiva de finalización.

¿Cómo se comunica el final de un stream?

Cuando trabajamos con HTTP tradicional, una petición termina cuando el servidor envía la respuesta y cierra la conexión. En Server-Sent Events (SSE), la cosa cambia bastante y existen distintas estrategias:

  • El backend cierra la conexión HTTP: Al emitir el último elemento del Flux, Spring WebFlux da por completada la respuesta y cierra el socket TCP.
  • El último mensaje incluye una marca explícita: Como por ejemplo un campo "isFinal": true o un evento especial como event: complete.
  • La conexión permanece abierta indefinidamente: A la espera de nuevos eventos futuros (ideal para notificaciones o cotizaciones).

El backend en Java (Spring WebFlux):

En el controlador de Spring Boot, emitir un stream finito requiere apenas unas líneas gracias al tipo de retorno Flux<T> y al content-type reactivo:

@GetMapping(value = "/technologies", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ApiDescription> getTechnologiesStream() {
    return technologyService.getTechnologies()
        .delayElements(Duration.ofSeconds(1)); // Emisión espaciada en el tiempo
}

El caso real: La trampa de EventSource y el misterio de las 10 peticiones

Durante el desarrollo de esta demo me encontré con un problema fascinante que resume a la perfección el desafío de comunicar el fin de un flujo.

Para demostrar que Netty y Spring WebFlux no bloquean hilos ante múltiples clientes, agregué un botón para simular 10 peticiones concurrentes a Tecnologías. Cada una abre su propia conexión SSE en paralelo.

El síntoma desconcertante:

Al hacer clic, las 10 conexiones se abrían en simultáneo, los mensajes iban llegando fluidamente a cada fila de la tabla y el estado marcaba "Éxito". Pero en la milésima de segundo en que llegaba el último mensaje... ¡las 10 solicitudes cambiaban su estado a "Error"!

¿Qué estaba pasando? ¿Por qué 10 peticiones que recibieron todos sus datos terminaban marcadas con error?

La paranoia de la especificación W3C

La API nativa del navegador EventSource fue concebida en su origen para flujos infinitos. Por especificación, cuando el servidor web completa su Flux y cierra la conexión HTTP, el navegador no piensa: "¡Genial, ya terminó!". Al contrario, entra en pánico:

“¡Se cortó la conexión inesperadamente! Voy a poner el estado en CONNECTING (0), disparar el evento onerror y reintentar reconectar en 3 segundos.”

Noten el detalle crucial: eventSource.readyState nunca pasa a CLOSED (2) por sí solo cuando el servidor corta la transmisión. Se queda en CONNECTING.

Si en el frontend manejamos el error de forma ingenua:

eventSource.onerror = (err) => {
  // ❌ NUNCA da true porque el navegador lo tiene en 0 (CONNECTING) intentando reconectar
  if (eventSource.readyState === EventSource.CLOSED) {
    observer.complete();
  } else {
    // 💥 ¡PUM! Tratamos el cierre normal del backend como un error de red fatal
    observer.error(err);
    eventSource.close();
  }
};

El Observable de RxJS recibía una señal de error() justo al terminar, lo que provocaba que el bloque catchError reemplazara el resultado exitoso por un estado de fallo.

La solución en Angular + RxJS

Para solucionar esto de raíz, el servicio frontend debe distinguir entre streams finitos (como tecnologías y ventajas) y streams infinitos (como las métricas de memoria):

  1. Llevamos el registro de si ya hemos recibido datos: hasReceivedData = true.
  2. Cuando el stream es finito y se dispara onerror después de haber recibido datos: sabemos con 100% de certeza que el servidor completó el Flux y cerró la conexión HTTP limpiamente. Cerramos el EventSource y llamamos a observer.complete().
  3. Si onerror ocurre sin haber recibido ningún dato previo, entonces sí se trata de una falla auténtica (servidor caído, timeout, error 500) y emitimos observer.error(err).
// ✅ Manejo robusto de cierre de stream finito en Angular
eventSource.onerror = (error) => {
  if (isFinite) {
    eventSource.close(); // Frenamos el reintento automático del navegador
    this.zone.run(() => {
      if (hasReceivedData) {
        observer.complete(); // Terminación triunfal y limpia
      } else {
        observer.error(error); // Error real previo a la recepción
      }
    });
  }
};

Con este cambio, las 10 peticiones simultáneas reciben sus eventos reactivos y, al finalizar, permanecen orgullosamente en verde con estado de éxito.

Las métricas son otro tipo de stream

Las métricas de memoria funcionan de una manera diferente. La API puede enviar periódicamente la memoria usada, libre y total. Angular recibe el valor más reciente y lo presenta como un resumen visual.

En lugar de mostrar solamente una tabla, la interfaz puede mostrar:

  • Memoria usada.
  • Memoria libre.
  • Memoria total.
  • Porcentaje de memoria utilizada.

Este tipo de información es un buen ejemplo de cuándo tiene sentido una conexión continua: el usuario está observando el estado actual del servidor y no una respuesta que deba terminar.

Lo que aprendí desde Angular

  • Un observable no siempre representa una respuesta inmediata; también puede representar un flujo que permanece abierto.
  • El frontend debe diferenciar entre datos, estados de conexión y errores de transporte.
  • En SSE, el cierre normal de un stream finito por parte del servidor dispara onerror en el navegador; debemos interpretar ese cierre como una finalización (complete) si los datos ya fueron emitidos.
  • Una conexión abierta no es necesariamente un problema si transporta telemetría continua.
  • La interfaz debe explicar al usuario qué está ocurriendo mientras llegan los datos para brindar una experiencia fluida e interactiva.
  • No conviene inventar un final contando mensajes o esperando algunos segundos a ciegas.

WebFlux no significa que todo sea automáticamente mejor

WebFlux resulta muy útil cuando necesitamos trabajar con muchas conexiones, operaciones de entrada y salida o datos que llegan progresivamente. Sin embargo, también agrega conceptos nuevos: publishers, subscribers, Mono, Flux, backpressure y conexiones que pueden permanecer abiertas.

El beneficio aparece cuando el problema realmente necesita ese modelo. Si una operación es pequeña y debe devolver una respuesta completa, el modelo tradicional puede ser más simple de entender y mantener.

Conclusión

Consumir una API reactiva desde Angular no consiste únicamente en recibir JSON. También implica comprender el ciclo de vida del flujo: cuándo comienza, qué mensajes envía, cuánto tiempo permanece abierto y cómo comunica que terminó.
