Mi primera experiencia consumiendo una API reactiva con WebFlux desde Angular

Cuando entramos a una página web normalmente esperamos una respuesta completa: hacemos clic en un botón, esperamos unos segundos y recibimos todos los datos juntos. Una API reactiva cambia un poco esta idea: puede comenzar a enviar información apenas la tiene disponible, sin esperar a construir una respuesta enorme.

En este artículo cuento, de forma sencilla, qué aprendí al conectar una aplicación Angular con una API construida con Spring WebFlux.

¿Qué intentaba mostrar?

La demo tiene tres tipos de información:

  • Tecnologías utilizadas para construir la API.
  • Ventajas de utilizar un enfoque reactivo.
  • Métricas de memoria del servidor en tiempo real.

La idea no era solamente mostrar una lista. Quería que el usuario pudiera ver cómo los datos llegan progresivamente desde el backend.

¿Qué significa que una API sea reactiva?

En lugar de pensar únicamente en una respuesta única, podemos pensar en un flujo de datos. Ese flujo puede emitir un mensaje, esperar un momento y emitir otro. El frontend escucha ese flujo y actualiza la pantalla cada vez que llega un nuevo elemento.

Una forma simple de imaginarlo es esta:

El backend no dice solamente: “aquí tienes todos los datos”.

Dice: “aquí tienes el primer dato”, luego “aquí tienes el siguiente” y después “aquí tienes otro”.

La conexión entre WebFlux y Angular

Para esta demostración utilicé Server-Sent Events, conocidos como SSE. El navegador abre una conexión con el servidor y queda escuchando los mensajes que llegan por ella.

Desde Angular, el consumo se realiza mediante EventSource. Cada vez que el servidor envía un evento, Angular recibe el texto, lo convierte desde JSON y actualiza la vista.

Flujo básico:

  1. Angular abre la conexión.
  2. WebFlux comienza a emitir datos.
  3. El navegador recibe cada evento.
  4. Angular actualiza la interfaz.

Lo primero que aparece en la pantalla

En la demo, la API puede comenzar enviando un mensaje de bienvenida:

Bienvenido y gracias por pasar por mi primera API REST reactiva.

Después puede explicar qué está ocurriendo:

  • “Paso a comentarte brevemente las tecnologías utilizadas”.
  • “Java 21 aporta mejoras de rendimiento”.
  • “Spring WebFlux utiliza un modelo no bloqueante”.

Para una persona que visita el portfolio, esta narración es importante. No tiene que conocer todos los detalles técnicos para entender que la información está llegando paso a paso.

Una conexión puede permanecer abierta

Durante las pruebas apareció una diferencia importante entre un stream finito y uno continuo.

El stream de métricas está pensado para permanecer abierto, porque el servidor sigue enviando valores nuevos. En cambio, tecnologías y ventajas podrían enviar una cantidad limitada de mensajes, aunque la conexión no se cierre automáticamente.

Esto tiene una consecuencia:

Que dejen de llegar mensajes no significa necesariamente que la conexión haya terminado.

Si el backend mantiene abierta la conexión, el frontend no puede adivinar si el stream terminó o si simplemente está esperando el próximo mensaje. Por eso no conviene utilizar un tiempo de espera como prueba definitiva de finalización.

¿Cómo se comunica el final de un stream?

Existen varias opciones:

  • El backend cierra la conexión cuando termina de enviar los datos.
  • El último mensaje incluye una marca como isFinal: true.
  • El protocolo utiliza un evento especial para indicar el final.

La opción más clara para una aplicación que está aprendiendo es utilizar un mensaje explícito. De esa manera, el frontend sabe qué ocurrió y no tiene que contar mensajes ni suponer que una pausa significa el final.

Las métricas son otro tipo de stream

Las métricas de memoria funcionan de una manera diferente. La API puede enviar periódicamente la memoria usada, libre y total. Angular recibe el valor más reciente y lo presenta como un resumen visual.

En lugar de mostrar solamente una tabla, la interfaz puede mostrar:

  • Memoria usada.
  • Memoria libre.
  • Memoria total.
  • Porcentaje de memoria utilizada.

Este tipo de información es un buen ejemplo de cuándo tiene sentido una conexión continua: el usuario está observando el estado actual del servidor y no una respuesta que deba terminar.

Lo que aprendí desde Angular

  • Un observable no siempre representa una respuesta inmediata; también puede representar un flujo que permanece abierto.
  • El frontend debe diferenciar entre datos, estados de conexión y errores.
  • Una conexión abierta no es necesariamente un problema.
  • La interfaz debe explicar al usuario qué está ocurriendo mientras llegan los datos.
  • No conviene inventar un final contando mensajes o esperando algunos segundos.

WebFlux no significa que todo sea automáticamente mejor

WebFlux resulta muy útil cuando necesitamos trabajar con muchas conexiones, operaciones de entrada y salida o datos que llegan progresivamente. Sin embargo, también agrega conceptos nuevos: publishers, subscribers, Mono, Flux, backpressure y conexiones que pueden permanecer abiertas.

El beneficio aparece cuando el problema realmente necesita ese modelo. Si una operación es pequeña y debe devolver una respuesta completa, el modelo tradicional puede ser más simple de entender y mantener.

Conclusión

Consumir una API reactiva desde Angular no consiste únicamente en recibir JSON. También implica comprender el ciclo de vida del flujo: cuándo comienza, qué mensajes envía, cuánto tiempo permanece abierto y cómo comunica que terminó.
