Capítulo 5 — Mi primera experiencia aplicando TDD

Desarrollo guiado por pruebas (Test-Driven Development) en el núcleo de la aplicación.

Fleet-FiftyFifty · Parte 5

Pensé que hacer TDD era escribir el test antes que el código

Mi primera experiencia aplicando TDD en Fleet-FiftyFifty me hizo descubrir que el verdadero desafío no era escribir el test, sino decidir qué debía probar.

¿Qué pruebo primero?

Bueno amigos, lo prometido es deuda.

Después de definir el dominio y elegir una arquitectura hexagonal para Fleet-FiftyFifty, llegó el momento de empezar a escribir código.

Y decidí probar algo que hasta ahora no había aplicado de esta manera: TDD.

La idea parecía sencilla: primero el test, después el código.

Pero cuando abrí el IDE apareció la pregunta:

¿Qué pruebo?

Y ahí descubrí que ese era el verdadero desafío.

Empecé por los ingresos

Decidí comenzar por una de las partes más importantes del negocio: los ingresos de la sociedad.

Un ingreso necesita representar algunas cosas muy concretas:

  • Quién recibió el dinero.
  • En qué plataforma se generó.
  • Cómo se recibió.
  • Cuánto dinero representa.

Por ejemplo: 

new Income(
    FleetRole.DRIVER,
    Platform.DIDI,
    PaymentMethod.CASH,
    Money.of("50000.00")
);

A partir de ahí pude construir mi primer escenario de prueba.

Mi primer escenario

Total $141.000
Owner $38.000
Driver $103.000
Reparto 50 / 50

Si el total es de $141.000 y el reparto es 50/50, cada uno debería quedarse con:

$70.500

Pero el dinero real ya fue recibido de forma diferente. El Driver tiene $103.000 y el Owner $38.000.

Por lo tanto:

  • Driver → Debtor
  • Owner → Creditor
  • Transferencia → $32.500

Y todo eso terminó en un test

El escenario anterior terminó convirtiéndose en mi primer test de dominio para WeeklyConsolidation. 

@Test
void shouldCalculateConsolidationWithDefaultFiftyFiftySplit() {

    WeeklyConsolidation consolidation =
            WeeklyConsolidation.ofDefaultSplit();

    // Ingresos...

    BalanceResult balance =
            consolidation.calculateBalance();

    assertEquals(FleetRole.DRIVER, balance.debtor());
    assertEquals(FleetRole.OWNER, balance.creditor());
    assertEquals(
        Money.of("32500.00"),
        balance.amount()
    );
}

El test comenzaba fallando porque todavía no existía toda la implementación necesaria para satisfacer ese comportamiento.

Y ahí comenzó realmente el trabajo.

El test me obligó a pensar en el negocio

Esta fue probablemente la parte que más me sorprendió.

El test no solamente me servía para validar código. Me estaba obligando a definir qué significaba que Fleet-FiftyFifty funcionara correctamente.

Antes de poder comprobar el comportamiento tuve que tener claro qué era un ingreso, quién lo recibía, cómo se calculaba el total y cómo se determinaba el balance entre las dos partes.

Y eso terminó guiando la construcción de las entidades y comportamientos del dominio.

No salió perfecto

Este tampoco es un post para decir que descubrí la fórmula perfecta para hacer TDD.

Mi primer test terminó comprobando bastantes cosas dentro del mismo escenario.

Viéndolo ahora, probablemente algunas responsabilidades podrían probarse de forma más aislada.

Pero justamente de eso se trata esta saga.

Estoy construyendo una aplicación real, tomando decisiones, equivocándome y aprendiendo durante el proceso.

Lo que me llevo de esta etapa

Empecé pensando:

"Tengo que escribir un test."

Y terminé pensando:

"Primero tengo que entender exactamente qué significa que el negocio funcione."

Para mí, ahí es donde TDD empezó a tener verdadero sentido.
