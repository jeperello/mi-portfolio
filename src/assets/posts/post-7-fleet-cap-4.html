Si bien desde la teoría ya entendía el concepto, siempre que realizo la práctica es cuando realmente lo comprendo.

Siendo sincero... ¿Esto es sobreingeniería? 😥

Elegí la Arquitectura Hexagonal en parte porque está de moda. Es una realidad: muchas son las empresas que la están utilizando y muchas buscan profesionales con experiencia en ella. Por lo tanto, decidí implementarla, aprenderla, entenderla y aplicarla en un proyecto real. ¿Qué mejor forma de aprender algo que en la práctica misma?

Sin embargo, si piensan que es sobreingeniería implementar esto y separar el dominio en Hexagonal para Fleet-FiftyFifty, tienen toda la razón. Para la lógica del negocio de esta app que hoy resuelve una liquidación semanal de Uber/DiDi 50/50, es un exceso de arquitectura.

100% podría haberlo resuelto con un @Service gigante y un par de entidades JPA en 20 minutos.

El descubrimiento al ordenar el código

Hay algo que descubrí al implementar esta arquitectura tan comentada. Al comenzar a ordenar el proyecto como esta lo exige, me di cuenta del verdadero potencial que tiene.

El código base, o el “core” como se conoce en mi aplicación, no debería de cambiar prácticamente nunca. La lógica principal (calcularGastos, calcularGanancias, establecerDiferenciaDePago) estará ligada a código puramente Java, para que nunca dependa de frameworks, de sus versiones ni de nada externo.

Java Puro: Sin anotaciones ni frameworks (Only Java Code)

Para garantizar que mi dominio no sepa que existe Spring Boot, la regla fue estricta: en el paquete domain solo entra código Java puro. Nada de @Entity, @Autowired, @Table ni anotaciones de JSON.

Un ejemplo de un objeto de dominio puro dentro del proyecto:

public record ProfitSplit(BigDecimal ownerPercentage, BigDecimal driverPercentage) {
    public ProfitSplit {
        if (ownerPercentage.add(driverPercentage).compareTo(new BigDecimal("100")) != 0) {
            throw new IllegalArgumentException("Los porcentajes deben sumar 100");
        }
    }
}

Las reglas de redondeo (usando HALF_UP a escala 2) y la determinación de quién queda como Debtor y quién como Creditor se calculan directamente en entidades puras sin tocar infraestructura: 

public class WeeklyConsolidation {
    private final Money totalOwnerIncome;
    private final Money totalDriverIncome;
    private final ProfitSplit split;

    public BalanceResult calculateBalance() {
        Money total = totalOwnerIncome.add(totalDriverIncome);
        Money targetShare = total.multiply(split.ownerPercentage());
        
        // Lógica pura de negocio para determinar las diferencias de pago
        return BalanceResult.of(total, targetShare);
    }
}

Desacoplando con Puertos y Adaptadores

Para conectar este mundo aislado con la infraestructura exterior definimos interfaces:

  • Inbound Ports (Puertos de Entrada): Casos de uso como ConsolidateWeeklyEarningsUseCase (operaciones que expone la aplicación).
  • Outbound Ports (Puertos de Salida): Interfaces como SaveConsolidationPort (lo que el dominio necesita guardar/recuperar sin saber qué BD se utiliza).

Spring Boot, los controladores REST y Spring Data JPA terminan siendo simples Adapters que viven fuera del núcleo, en el paquete de infrastructure.

Ganancias obtenidas hasta el momento 🚀

  • Dominio hiper-testeable: Puedo probar toda la lógica financiera con JUnit sin levantar el contexto de Spring en milisegundos.
  • Cero impacto en el core: Si el día de mañana decidimos cambiar la BD, queremos que otra app consuma sus datos, o cambiar el frontend, el core no cambiará. Agregando un adapter podemos hacer lo que queramos sin impactar el código fuente de la lógica fundamental del negocio.
  • Evolución mobile: El día de mañana sueño con tener una app en alguna Play Store, y este código es superadaptable y transportable.
  • Desacople real: Experimentar la verdadera práctica del desacople en código de producción.

Lo que más me costó de este paso 🧠

Luego de años de práctica con Spring Boot, no usar anotaciones hoy en día me resulta raro: Only Java Puro.

Esto realmente, aunque suene raro viniendo de un Java Developer, escribir Java puro sin ningún framework hoy en día me resultó muy extraño. Fue lo que más me costó: cambiar el chip que tanto tiempo también me había costado crear.
